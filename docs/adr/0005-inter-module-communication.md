# ADR-0005. 모듈 간 통신은 공개 API와 이벤트로만 한다

- 상태: 승인
- 날짜: 2026-09-24

## 맥락

같은 프로세스 안에서는 다른 모듈의 어떤 클래스든 호출할 수 있다. 이걸 막지 않으면 모듈 사이의 호출 지점이 코드 전체에 흩어진다. 그러면 나중에 모듈을 떼어낼 때 네트워크 호출로 바꿔야 할 곳을 전부 찾아 고쳐야 한다.

## 결정

### 1. 동기 호출: 상대 모듈의 `api` 파사드를, 아웃바운드 포트를 통해서만 호출한다

```
order 모듈                                          inventory 모듈
┌────────────────────────────────────────┐        ┌─────────────────────────┐
│ PlaceOrderService                      │        │                         │
│   └─▶ ReserveStockPort (port/out)      │        │                         │
│         ▲                              │        │                         │
│         │ 구현                          │        │                         │
│ InventoryAdapter (infrastructure) ─────┼───────▶│ InventoryFacade (api)   │
└────────────────────────────────────────┘        └─────────────────────────┘
```

- `order`의 유스케이스는 `inventory`를 모른다. 자기가 정의한 `ReserveStockPort`만 안다.
- `inventory`를 아는 곳은 `InventoryAdapter` **한 곳**뿐이고, 그마저도 `inventory.api`만 안다.
- MSA로 전환할 때는 `InventoryAdapter`만 HTTP 클라이언트로 교체한다.

### 2. 비동기: 이벤트로 알린다

- 다른 모듈이 반응해야 하는 사실(예: 주문 완료)은 이벤트로 발행한다.
- 발행하는 쪽은 누가 구독하는지 모른다.
- Spring Modulith의 `@ApplicationModuleListener`와 이벤트 발행 저장소(Event Publication Registry)를 쓴다. 이 저장소는 사실상 트랜잭셔널 아웃박스 역할을 한다. P2에서 도입한다.

### 3. 도메인 이벤트와 통합 이벤트를 구분한다

| | 도메인 이벤트 | 통합 이벤트 |
|---|---|---|
| 위치 | `domain/event/` | `api/event/` |
| 대상 | 모듈 내부 | 다른 모듈 (전환 후에는 다른 서비스) |
| 변경 | 도메인과 함께 자유롭게 바뀐다 | 외부 계약이라 호환성을 지켜야 한다 |
| 전환 후 | 그대로 | Kafka 메시지 스키마가 된다 |

## 결과

- 전환 시 바꿔야 할 지점이 모듈마다 `infrastructure/adapter`와 이벤트 발행 설정으로 좁혀진다.
- 비용: 모놀리식 안에서는 메서드 호출 하나로 끝날 일에 포트, 어댑터, 파사드 세 단계를 거친다.
- 다시 볼 것: 같은 프로세스 안에서는 동기 호출도 한 트랜잭션에 묶인다. 전환하면 이 전제가 깨진다. 그때 무엇이 깨지는지가 시리즈 후반부의 핵심 주제다.
