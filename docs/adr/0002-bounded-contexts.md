# ADR-0002. 바운디드 컨텍스트를 여섯 개 모듈로 나눈다

- 상태: 승인
- 날짜: 2026-09-24

## 맥락

도메인은 이커머스 주문이다. 누구나 설명 없이 이해할 수 있고, MSA 전환에서 다루고 싶은 문제(트랜잭션 경계, 동시성, 외부 연동, 조회 조합)가 자연스럽게 등장한다.

모듈을 나누는 기준은 두 가지로 잡았다.

1. **언어가 달라지는 곳**: 같은 "상품"이라도 카탈로그에서는 이름과 가격이고, 재고에서는 수량과 예약이다.
2. **변경 이유와 부하 특성이 달라지는 곳**: 함께 바뀌는 것은 묶고, 다르게 바뀌는 것은 나눈다.

## 결정

| 모듈 | 책임 | 허용 의존 |
|---|---|---|
| `member` | 가입, 인증, 회원 정보 | 없음 |
| `catalog` | 상품 정보 (이름, 가격, 설명) | 없음 |
| `inventory` | 재고 수량, 예약, 차감 | 없음 |
| `payment` | 결제, 외부 PG 연동 | 없음 |
| `order` | 주문 생성과 상태 흐름. 다른 모듈을 조율 | member, catalog, inventory, payment의 `api` |
| `notification` | 알림 발송. 이벤트에 반응만 한다 | order, member의 `api` |

```
notification ──▶ order ──┬──▶ member
     │                   ├──▶ catalog
     │                   ├──▶ inventory
     │                   └──▶ payment
     └──────────────────────▶ member
```

허용 의존은 각 모듈의 `package-info.java`에 `@ApplicationModule(allowedDependencies = ...)`로 선언하고, `ModularityTests`가 검증한다. 의존은 한 방향으로만 흐르고 순환이 없다.

### 상품을 catalog와 inventory로 나눈 이유

하나의 `Product` 애그리거트에 재고 수량을 넣으면 다음 문제가 생긴다.

- **쓰기 경합**: 재고는 주문마다 차감되는 핫 로우다. 상품 정보 수정(가격 변경 등)과 재고 차감이 같은 행에서 락을 다툰다.
- **변경 이유가 다르다**: 상품 정보는 운영자가 가끔 바꾸고, 재고는 주문이 들어올 때마다 바뀐다.
- **확장 특성이 다르다**: catalog는 읽기 위주라 캐시가 잘 먹고, inventory는 쓰기 위주라 동시성 제어가 핵심이다.

두 모듈은 `productId`로만 연결되고, 서로를 의존하지 않는다.

## 결과

- 성능 편(P4)에서 재고 동시성 전략을 catalog와 무관하게 실험할 수 있다.
- notification은 들어오는 의존이 없는 가장자리 모듈이라 첫 추출 대상으로 삼기 좋다.
- 비용: 상품 등록 시 catalog와 inventory 양쪽에 데이터를 만들어야 한다. 모놀리식 안에서는 하나의 유스케이스로 조율하고, 전환 후에는 이것도 분산 정합성 문제가 된다.
- 다시 볼 것: 모듈 간 공통 값 객체(`Money` 등)를 공유 커널로 둘지는 P1에서 결정한다.
